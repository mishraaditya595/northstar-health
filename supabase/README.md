# NorthStar Supabase — development backend

**Status:** Six of seven committed P2-01 migrations are recorded on the **development** Supabase project; the final completed-only migration must be reconciled before P2-05 can be applied there. P2-01 Supabase groundwork, P2-02 authentication, P2-03 outbox and P2-04 authenticated foreground uploader are merged in PRs #13–#16. P2-05 server progress aggregation is implemented in [PR #17](https://github.com/mishraaditya595/northstar-health/pull/17) (consult GitHub for its live merge state); production rollout still needs live Auth/RLS E2E and physical-device QA. See [ADR-0005](../docs/adr/0005-mandatory-auth-and-workout-sync.md) and [Cloud Sync Contract](../docs/CLOUD_SYNC.md).

Eight ordered migrations under `supabase/migrations/` create and then harden `workout_records`, `workout_sync_operations`, `northstar_private.workout_owner_cursors` and the authenticated `sync_workout` RPC. The initial migration is retained because it was applied to the dev instance. The hardening adds strict required-field checks and typed values, hashed 90-day receipts, per-owner change cursors, and conditional revision updates. The third migration fixes a validator special-form spelling error. The fourth adds owner-triggered expired-receipt pruning and safely revokes public execution of the hosted-only RLS event-trigger function if present; the fifth and sixth close numeric, UUID and tombstone bugs; the seventh restricts sync to completed workouts (ADR-0005), and the eighth (P2-05, **not applied to hosted development in this review**) derives original-local completion dates and exposes an owner-scoped read-only progress RPC.

`supabase/tests/workout_sync.test.sql` is a rolled-back synthetic pgTAP suite (64 assertions) covering account boundaries, JSON validation, replay, deletion and processing. `supabase/tests/workout_progress.test.sql` now includes 65 assertions covering per-day progress, missing-load and missing-counter semantics, INSERT/UPDATE/DELETE permissions, UTC output, extreme dates, correction/tombstones and owner isolation (129 total when combined with the 64 original sync assertions). Refer to the current PR CI job for the actual result. The `.github/workflows/supabase_sql.yml` job starts a clean local database, replays migrations, and runs `supabase test db`. Run the same commands locally or in CI and record its result in the PR before merge. The connected development Supabase project currently reports six migration versions, while the repository carries seven already-merged P2-01 migrations plus draft P2-05. Reconcile the development migration history before any hosted P2-05 deployment. A read-only precheck on 26 October 2026 found zero active completed dev records and zero malformed/zone-free timestamps. The P2-05 backfill uses a transaction-local UTC session time zone; on populated production databases its backfill UPDATE and ordinary CREATE INDEX can block writes, so profile the table and schedule maintenance or split into batched/backfill and concurrently indexed deployment. Real two-connection concurrency tests and release/privacy gates remain open.

Do not commit private or service-role keys, database credentials, bearer tokens, real workout records, raw platform health data, or full ObjectBox database files. Flutter may use a public project URL and publishable key with authenticated sessions; only the backend controls privileged storage and server computations.

**Rollback:** Do not delete workout tables. Revoke authenticated RPC EXECUTE to halt cloud writes, preserve ObjectBox queues, then deploy a corrective migration. Do not replay an older vulnerable function over newer production migrations.
