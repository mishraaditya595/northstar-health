# P2-06 — Multi-device workout restore and conflict handling

**Status:** server-feed implementation slice ready for independent PR review on `feat/phase2-p06-restore-feed`. **P2-06 as a whole is not feature-complete or deployed.** P2-05 [PR #17](https://github.com/mishraaditya595/northstar-health/pull/17) was merged 2026-10-26.

## What slice 1 implements

- Additive migration `20261026083000_phase2_restore_change_feed.sql` defines authenticated, read-only `public.get_workout_changes(p_after_seq bigint default 0, p_limit int default 100, p_cursor_epoch uuid default null)`.
- The public read RPC is `SECURITY INVOKER`, pins `search_path`, derives the owner from `auth.uid()`, rejects missing, anonymous and malformed identity claims with SQLSTATE `28000`, and relies on existing owner-scoped SELECT RLS. `PUBLIC` and `anon` have no EXECUTE grant. No client INSERT/UPDATE/DELETE grant is introduced. A tightly scoped private `SECURITY DEFINER` helper, `northstar_private.current_workout_restore_state()`, accepts **no owner parameter**, repeats the identity check and reads the caller's authoritative counter and the global restore epoch in one statement snapshot. It does **not** grant clients SELECT on the private counter or epoch tables. `northstar_private.rotate_workout_restore_epoch()` is `SECURITY INVOKER`, has no mobile execution grants, and can only be run by the privileged database operator.
- Stable **per-owner** `server_change_seq` is used for `p_after_seq`. The response is `{schema_version:1, cursor_epoch:<uuid>, cursor_reset:<boolean>, next_cursor:<number>, has_more:<boolean>, changes:[...]}`. A brand-new device may call with `(p_after_seq:0,p_cursor_epoch:null)` to bootstrap; **every request after that must echo the previously returned epoch** alongside its saved cursor. A nonzero cursor with a missing epoch is treated as a reset. Each change contains `workout_id`, `server_revision`, `change_seq`, `deleted`, and `payload`. The payload is the validated existing P2-01 phone-workout snapshot or JSON `null` for a deletion tombstone; the feed never contains health platform measurements or account IDs.
- Limits: cursor must be a nonnegative 64-bit integer, page size 1–200 inclusive. Reads are ordered by `server_change_seq`; at most `p_limit + 1` current rows are scanned to determine `has_more`. An ordinary empty result returns the caller's unchanged cursor. If the cursor is greater than the owner's authoritative `last_change_seq`, **or** the supplied epoch differs from the server's epoch, `cursor_reset:true` is returned with the **new server `cursor_epoch`**, `next_cursor:0`, `has_more:false`, `changes:[]`. Epoch mismatch still resets when new writes have already overtaken the old device cursor, closing the numeric-only recovery gap. This is a control response, not a change page. The mobile client must reconcile pending/acked local revisions before restarting from zero and must **not** delete any local workout or overwrite unsynced data just to reset a cursor. Owner-specific change index already exists; no new index or row rewrite.
- On a brand-new device restoring from `0`, the feed **intentionally includes tombstones for workouts that device has never seen**. The importer should not display those as phantom workouts; it must still retain enough deletion identity to prevent resurrection and advance its cursor durably only after safe processing. The feed is a **current-state** feed, not a complete event log. Earlier revisions overwritten by later corrections are intentionally absent; the latest nondeleted row or durable tombstone is returned. This is appropriate for state restore, **not** an audit trail.
- `supabase/tests/workout_restore_feed.test.sql` is a transactional pgTAP suite with synthetic users (**76 assertions; pending revised CI validation**). It checks grants/RLS, missing, anonymous and malformed JWT claims; invalid arguments; private epoch-table isolation; missing/mismatched epochs; cursor-reset handling against the authoritative private counter; exactly-full and truncated pages; cursor-to-last-item consistency; corrections and idempotent replay; tombstones and owner isolation. A synthetic privileged test covers a counter greater than the highest visible row, then rotates the epoch and confirms the stale device resets even while numerically behind the counter. **Concurrency limitation:** pgTAP here uses a single SQL session; the reviewer separately verified ordering across two concurrent sessions, but that check is not automated. This is not live signed-JWT network verification.

## Restore epoch: mandatory operational dependency

**A stored database epoch cannot prove its own history.** Restoring a snapshot also restores the epoch value in that snapshot, so `get_workout_changes` cannot intrinsically infer that a database restore occurred. To guarantee detection, operations **must rotate the epoch after every database restore, including PITR or snapshot replacement, before any authenticated read/write traffic resumes**. If this procedure is skipped, a stale device with an epoch equal to the restored snapshot's epoch can still miss updates. Do not describe the epoch mechanism as automatically fail-safe without this step.

The privileged rotation command and recovery checklist live in [Database restore and cursor-epoch runbook](../../../supabase/RESTORE_RUNBOOK.md). Rotation invalidates **all devices' stored epochs** (one global epoch), conservatively causing a full owner-scoped reconciliation for each account. No history is deleted as part of epoch rotation.

**Future mobile importer contract:** atomically store `cursor_epoch` with `next_cursor` and imported workout data in the same owner-bound ObjectBox transaction. On `cursor_reset:true`, treat the response as a recovery signal: reconcile/preserve unsynced local operations and tombstones, invalidate the old cursor, fetch from `0` under the new epoch, and do not blindly overwrite local content. A race with rotation after a page read is detected on the next request; do not claim a new epoch is durable until the page's data is durably imported.

## Required next slices (not implemented)

1. **Read-only authenticated mobile pull transport and strict DTO decoder.** Request using the active account's non-anonymous valid JWT; validate `schema_version`, type/UUID shape, monotonic cursor, item order and payload before touching ObjectBox. Never log raw workout content. Reject malformed responses without advancing cursor.
2. **Safe ObjectBox importer.** In the same owner-bound write transaction, atomically persist incoming workout/session/exercise/set snapshots and a durable per-owner pull cursor. Transaction rollback must keep the old cursor. Workouts must restore as `completed` only; no plans, timers, checkpoints, imported/watch sessions or physiological data. Keep original UTC instants and offset; preserve UUIDs, unit, reps, load and RPE. Do not enqueue a restored snapshot as a new phone upload.
3. **Collision and conflict handling.** Never overwrite a local workout that has a pending, blocked, conflicting, or ambiguous operation. Preserve dirty local content. Present explicit choice/review; do not silently choose local or remote. Persist the server revision needed for future compare-and-swap. A remotely deleted workout becomes a local tombstone and cannot be resurrected by queued updates.
4. **Queue fairness and dependencies.** The P2-04 first-500 pending scan can starve eligible later rows. Implement a bounded cursor/fair scan that can reach eligible operations without sending higher workout revisions past a blocked/conflicting predecessor. Expose a durable dependency-paused state, never silently drop data.
5. **Lifecycle + multi-device reconciliation.** Pull on authenticated foreground launch and resume, serialize with uploads to avoid inconsistent version mapping, tolerate offline/timeout and account switch mid-flight, persist resumable cursor, replay safely after a crash, test latest corrections and tombstones on devices A and B.
6. **Deletion and UX boundary.** Finish deletion command/outbox behavior, explicit conflict resolution and restore status (P2-06), then user-facing recovery/backup status, export and account deletion in P2-07.

## Rollback

The restore RPC is read-only; revoke authenticated EXECUTE on `get_workout_changes` if necessary. Preserve local outboxes, imported history, per-owner cursors and hosted records. Use forward-only corrective migrations; do not drop existing workout tables.
