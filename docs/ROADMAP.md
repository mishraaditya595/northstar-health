# BeyondRep implementation roadmap

**Initial foundation (merged PR #2):** Flutter demo screens, Performance V2 reference, adaptive light/dark design, Riverpod, routing, agent rules, ObjectBox package configuration, ADRs and CI. This is not a production health application.

## Production structure/bootstrap — merged scaffold

Flutter lives in `apps/mobile/` with version-controlled Android and iOS runners. Standalone non-recording native `apps/watch_os` and `apps/wear_os` scaffolds and the `contracts/workout_sync/v1` schema/fixtures are present. **Apple Watch target embedding is in source (stage 3); watch signing through Codemagic, companion distribution and physical-device verification are still release gates.**

## Phase 1 — Reliable offline workout logger

Implementation reports and PR scopes live under
[docs/implementation/](implementation/README.md). The foundation and
exercise/plan catalog and local session lifecycle engine (no UI) are implemented;
the active logging UI and rest timer have been merged in PR #10;
completed workout history/progress was merged in PR #11. Physical-device
persistence QA, backups, iOS build verification and accessibility remain
outstanding.

ObjectBox schema and generated model committed; domain models and repository boundary; plan/exercise editor, custom exercise catalog, live sets/reps/weight/RPE, rest timer, progress and session checkpoints; atomic durable write; model-migration and process-death tests. At Phase 1 this logger supported guests; Phase 2 replaces the public entry flow with mandatory initial sign-in, while preserving authenticated offline logging.

## Phase 2 — Mandatory accounts, automatic workout sync and server processing

[ADR-0005](adr/0005-mandatory-auth-and-workout-sync.md) removes guest login and keeps completed-only backup. Users must register/sign in before using BeyondRep. After initial verification, workouts remain editable offline using the securely bound account. Automatically queue each BeyondRep phone workout once the user finishes it; unfinished sessions stay local. Server validates and processes completed metrics. Implement owner-scoped RLS, strict DTO validation, request hashing, transactional outbox, server revision CAS, per-account cursors, restore/tombstones and conflict handling. There is no guest data to migrate; never reassign local workouts between accounts. Custom plans, exercise definitions outside history, local recovery checkpoints, preferences and health-platform observations stay local. P2-01 (backend), P2-02 (required account) and P2-03 (durable outbox) are merged. P2-04 automatic foreground uploader **merged in PR #16**, with account-matched JWTs, durable retry and CAS. P2-05 server progress aggregation **merged in PR #17** (not yet deployed to the hosted database). P2-06 restore, foreground orchestration, queue fairness, completed-workout deletion and reviewed conflict recovery were merged in PRs #18–#24. P2-07a account/sync UI (#25), P2-07b owner-scoped JSON cloud-history export (#27) and P2-07c freshly reverified, server-only permanent account deletion (#29) are **merged in source**, including ADR-0007's two user-confirmed uncertain-recovery exits. **None of these merges proves hosted deployment or native-device/security acceptance.** P2-08 end-to-end release QA remains pending; the former 4 MiB export ceiling is replaced in source by page-by-page streaming, which still needs physical-device memory verification. P2-04 remains foreground best-effort; real-account E2E and physical-device testing are release gates.

## Phase 3 — Permission-based platform health reads

Apple HealthKit and Android Health Connect for supported types; distinct per-feature permission prompts, source provenance and timestamps, platform aggregate queries, ephemeral local caches, revocation/unknown/stale behavior, background constraints and supported device matrix. No raw health measurements in Supabase.

**Phase 3 scope (ADR-0008):** daily summary of four metrics (sleep, steps, resting heart rate, weight), read-only, no health-value cache, per-account opt-in. The "ephemeral local caches" wording above is superseded for this phase: it uses none (ADR-0008). Implemented in source, not released or device-verified; see [p3-01](implementation/phase-3/p3-01-daily-health-summary.md) and the Phase 3 gates in [RELEASE.md](RELEASE.md).

**Health insights extension (ADR-0009, in progress, not released):** richer Health tab, 7/30-day trends and on-device scores, read fresh with nothing stored. Stages: (0) chart kit widgets in `lib/core/design/charts/`; (1) richer data and trends: reader range reads, domain layer, sleep score, overview cards, four detail screens, permissions update, Today row; (2) readiness score, hero card and Train note; (3) training tie-ins: muscle recovery from logged workouts, better-fit plan suggestion, joined insights. Stages 0-2 are merged on `main` (stage 2 is an on-device readiness score from HRV and resting HR against the 30-day baseline, last night's sleep score and sleep debt, shown as the Health tab hero card, a detail screen, a Train note and a once-per-day low-readiness note before a workout starts). Stage 3 is implemented in source: `muscleRecoveryProvider` now weighs completed working sets by reps (5 or more or unknown 1.0, under 5 0.7) and RPE (about ten hard sets saturate a group, a group under 0.1 counts as recovered on both Progress and Train, linear fade over 72 h for chest, back and legs and 48 h for shoulders, arms, core and small custom groups, sessions add up capped at 1; workout data only); the Train page shows a "Better fit today" suggestion and a recovery line per plan (works without a wearable); and two insights computed in memory from the last 30 days (sleep after training days vs other nights, resting heart rate the morning after the biggest sessions; at least 5 days on each side, 30 minutes or 3 bpm apart, starting at the first logged workout) show on Sleep detail and Heart detail; the Health tab shows one of the two, sleep first. The spec's other two insights (weekly volume vs readiness, weight vs strength trend), insights on Progress are not implemented. None of it is released or device-verified (device matrix in [RELEASE.md](RELEASE.md)). A health polish stage 1 (explain sheets and Health terms page, Today readiness hero and tiles, Train start card with a readiness strip and today's program workout) is implemented in source, not released or device-verified. A health polish stage 2 ([ADR-0011](adr/0011-read-workouts-from-health-platforms.md): workouts other apps saved to HealthKit / Health Connect, read fresh for 90 days and never stored, merged with overlapping BeyondRep sessions, shown in Activity, Progress history and the Today Workouts tile, and recent training load as a fifth readiness input) is implemented in source, not released or device-verified. An energy score stage 1 ([ADR-0013](adr/0013-energy-score.md): an "energy now" number on the Health tab hero and the readiness detail Today view, from the morning readiness start minus workouts, extra active energy and time awake plus naps, shown from 3 baseline days with a learning note, computed in memory and never stored) is implemented in source, not released or device-verified; stages 2 and 3 are not started, and other surfaces still show readiness. **Release gate:** because readiness is now scored from 3 baseline days on Today, Train, the pre-workout note, "Better fit today" and the watch, with no learning note there (that comes in stage 2), energy stage 1 must not ship to users without stage 2. Each stage ships and is reviewed on its own; device QA and store gates remain open.

**Training library (issue #63, [ADR-0010](adr/0010-shared-training-catalogue.md), in progress, not released):** a shared, versioned exercise/template/program catalogue published from Supabase. Stage 1 (catalogue backbone: JSON source and validator, immutable releases with a live pointer, two read RPCs for signed-in clients, generated publish/rollback migrations, release 1 with the 18 existing exercises, hosted access audit) is **published to the development Supabase project (release 1 live then), not released to users**; the live hosted audit is a manual gate. Stage 2 (phone cache and client: verified, atomically swapped catalogue file shared across accounts, daily background refresh, catalogue exercises in the exercise pickers and the Exercises page, copied into the account's ObjectBox store when picked) is **in source, not released or device-verified**; the device checks are open in [RELEASE.md](RELEASE.md). Stage 3 (specific muscles: exercises carry primary and secondary muscles from the catalogue, each logged workout keeps a snapshot that syncs and restores through two optional exercise arrays, muscle recovery, "Better fit today" and the body map use them with secondary muscles at half weight, an exercise detail screen shows them on the body map, and older workouts and custom exercises keep the coarse group behaviour) is **applied to the development Supabase project, not released to users or device-verified**; its migration `20261126010000_workout_exercise_muscles.sql` must be applied to any other project before an app build that uploads the arrays. Stage 4 (timed sets: `duration` exercises such as plank are logged in seconds with a start/stop timer and no reps field, plans can target seconds, and `duration_seconds` syncs, restores, exports and counts in history, progress and recovery) is **applied to the development Supabase project, not released to users or device-verified**; its migration `20261126020000_workout_set_duration.sql` must be applied to any other project before an app build that uploads it, and every install updated because older builds refuse the new key when restoring. Stage 5 (exercise content: release 2 grows the library from 18 to 240 original exercises across barbell, dumbbell, machine, cable, bodyweight, band, kettlebell and small equipment, with muscle group and equipment filters on the Exercises page and the picker) is **published to the development Supabase project (release 2 live then), not released to users or device-verified**. Stage 6 (workout templates: release 3 adds 16 original standalone templates, a Workouts entry on Train lists them with search and level chips, a template screen shows every exercise with sets, reps or seconds and rest, and "Start now" begins an unsaved workout while "Copy to My Plans" creates an independent, editable plan in one local transaction) is **published to the development Supabase project (release 3 live then), not released to users or device-verified**. Stage 7 (programs: release 4 adds 17 original programs and 22 program-only templates, Train gets a Programs entry and a Your program card, adding a program creates editable plans and a schedule in one local transaction, and today's workout can be started with its program day recorded on the session; all program data is local only) is **published to the development Supabase project (release 4 live, 19 of 19 migrations applied, checked read-only on 2026-11-26), not released to users or device-verified**. Stage 8 (Today and scheduling: Today shows the active program's workout, "Rest day" or "Done for today" with Start and Open program, plus a "Missed <weekday>: <workout>" line that starts the most recent missed day of the current program week with that date recorded; Your program tags every day Done, Missed, Today, Rest, Upcoming or Unavailable and starts older missed days; only the active program can start workouts; Workouts and Programs get goal, equipment I have and days-per-week filters; an optional `status: retired` on templates and programs hides them from the lists, with the validator and phone parser honouring it, and no new catalogue release in this stage) is **implemented in source, not released or device-verified**; program data stays local only and day statuses are computed fresh, never stored. Stage 9 (release verification: automated accessibility guideline, tablet and split-view layout and process-death tests, measured catalogue performance, and the ordered owner device script in [RELEASE.md](RELEASE.md)) is **automated verification done in source, device script open**; results are in [stage-9-verification.md](implementation/training-library/stage-9-verification.md). See [CATALOG.md](CATALOG.md) and the [design](superpowers/specs/2026-11-25-training-library-design.md).

## Phase 4 — Apple Watch companion and tablet layouts

Apple Watch recording plus wide-window layouts for tablets, designed together in the [Phase 4 design](superpowers/specs/2026-11-26-phase-4-watch-and-tablet-design.md) and built in stages that each ship and are reviewed on their own. Watch scope: record sets/reps/load, rest haptics and a native watchOS HealthKit workout session; local offline journal, phone pairing, reconnection ACK and app-background recovery; physical-device spikes may begin earlier in parallel to avoid late architecture surprises. No production dependency on an experimental engine without real tests.

**Stage 1 (tablet layouts, implemented in source, not released or device-verified):** on windows 840 dp and wider Today, Health, the five Health detail screens, Progress history, the Exercises, Workouts and Programs lists and Train use the width (two columns, card grids, list and detail side by side); narrower windows, portrait iPad and split view keep the single column. Layout primitives live in `lib/core/design/layout.dart`. The iPad simulator and split-view checks are open in [RELEASE.md](RELEASE.md).

**Stage 2 (message contracts and watch core, implemented in source, no UI, not device-verified):** [ADR-0012](adr/0012-apple-watch-companion.md); `contracts/workout_sync/v2` and `contracts/watch_link/v1` with synthetic fixtures and replay cases; Dart codecs and the watch account key in `lib/features/watch/domain/`; the `BeyondRepWatchCore` Swift package (codecs, event replay, session state machine, SQLite journal and outbox) tested on macOS CI. No transport, no screens, no HealthKit, no Supabase migration for `beyondrep_watch` yet.

**Stage 3 (phone-watch link, health glance and TestFlight embedding, implemented in source, not released or device-verified):** the phone builds `watch_link/v1` account binding, plans and health snapshots (`lib/features/watch/application/`) and pushes the latest of each over WatchConnectivity (a small Runner bridge, `ios/Runner/WatchLinkBridge.swift`); the watch app stores them in its journal and shows a read-only Home glance (readiness, sleep, resting HR, HRV, steps, plan names); a sign-out or account switch is designed to clear the previous account on the watch (the clear goes in the application context and as user info, and the watch orders clears and bindings by their send times so a replayed or late message cannot undo the newest one; not device-verified). The watch target is embedded in `Runner.xcodeproj` by `tool/embed_watch_target.rb` and built unsigned by the `ios-with-watch` CI job; the `mobile-ios-testflight` job now also carries it, with watch signing unverified until the first run. No Start button, no HealthKit, no workout recording. Device checks are open in [RELEASE.md](RELEASE.md).

**Watch glance redesign and sync status (a small stage between 3 and 4, implemented in source, not released or device-verified):** the watch app is two vertical pages, Home (readiness hero and an even 2x2 grid of sleep, resting HR, HRV and steps with a status line each) and Train (today's program workout, then the plans), with a Train button and a one-time crown hint; tiles, the hero and the status line open detail screens (sleep with stages, resting HR and HRV against the usual, steps, readiness factors, each with a 7-day trend). The optional `health_snapshot` fields (`week`, usual values, stage minutes, readiness factors) carry the data ([watch_link v1 README](../contracts/watch_link/v1/README.md)). The watch replies with an `ack`; the phone shows a top banner on Today when BeyondRep is not on a paired watch ("Show me how", "Not now") or the watch has not synced for 48 hours, a quiet "Apple Watch · synced" line at the bottom when it works, and an Apple Watch section on Account & sync; nothing is shown without a paired Apple Watch. ADR-0012 decision 4 is amended. Design: [spec](superpowers/specs/2026-11-27-watch-glance-redesign-and-sync-status-design.md), [plan](superpowers/plans/2026-11-27-watch-glance-redesign-and-sync-status.md). The Swift tests run in `watchos_smoke.yml` on the PR; device checks are open in [RELEASE.md](RELEASE.md).

**Stage 4a (phone import and `beyondrep_watch` origin, implemented in source, not released or device-verified):** the server accepts the cloud origin `beyondrep_watch` (migration `20261127090000_workout_origin_beyondrep_watch.sql`, deploy before any build that uploads it); restore, history, the outbox, upload validity and the account export keep that origin; the `completed_workout` body takes an optional `program_day`; the phone validates a `completed_workout` from the watch with the cloud-payload validator and commits workout, receipt and outbox entry in one ObjectBox transaction, then sends the `ack` (`stored`, `duplicate`, or `rejected` with reason `invalid`; a workout for another account gets no ack and a locally deleted one is never brought back); history rows and details show an "Apple Watch" tag; the watch's own HealthKit workout is hidden from outside workouts (ADR-0011 rule 3 amended); the account-deletion wipe is persisted and resent until the watch acks it. Nothing sends a completed workout from the watch yet, so none of this can be device-tested end to end. SQL runs only in `supabase_sql.yml` and Swift only in `watchos_smoke.yml`. See [the plan](superpowers/plans/2026-11-27-phase-4-stage-4a-watch-workout-import.md).

**Stage 4b (record workouts on the Apple Watch, implemented in source, not released or device-verified):** a person can start today's program workout, a plan or a quick workout on the watch, log sets with weight and reps side by side and the Digital Crown, answer an optional RPE, rest with a haptic, pause, add sets or exercises, finish and have the workout saved once to Apple Health and delivered to the phone, which stage 4a already imports and backs up. All rules live in `BeyondRepWatchCore` (journal version 6 with delivery state, a template with fresh exercise and set ids per workout, cursor, rest clock from events, completed-workout builder with shared golden cases in `contracts/watch_link/v1/cases/completed`, `WorkoutController` committing one journal transaction per action and finishing in two steps so a kill after the HKWorkout is saved never saves a second one); the watch app adds the HealthKit wrapper (`HKWorkoutSession`, `HKLiveWorkoutBuilder`; share `workoutType()`, read heart rate and active energy only), the screens, the `workout-processing` background mode and sending queued workouts over WatchConnectivity until the phone's `ack` removes them (a workout of another account stays queued and is never sent or deleted). The `completed_workout` carries the HKWorkout UUID only: no heart rate, calories or other health value. The Swift tests run in `watchos_smoke.yml`; device checks are open in [RELEASE.md](RELEASE.md). See [the plan](superpowers/plans/2026-11-27-phase-4-stage-4b-watch-workout-recording.md).

**Stage 4c (heart rate and calories on the phone, watch cleanup, cross-phone test, implemented in source, not released or device-verified):** the history detail of an Apple Watch workout shows its average and maximum heart rate and active energy under "From Apple Health", read fresh through the stored HKWorkout receipt (existing read types, no new permission) and never stored, uploaded or exported; the section hides when Health is disconnected, the HKWorkout is gone or no value exists. The watch drops an account's plans, health and binding when the phone has not refreshed them for 90 days (never during a workout, never unsent workouts) and keeps only the 20 newest clear tombstones (`WatchJournal.pruneStale`). A Dart test pins the phone side (a watch workout resent to a second phone after deletion, with a faked server conflict, ends in conflict handling and no silent resurrection) and a pgTAP case pins the server side (the tombstone answers `conflict` with reason `deleted` at expected revision 0) (requirement b of the original 4b). Live handoff, workout mirroring and phone commands are stage 5. Swift and pgTAP tests run on CI only; device checks are open in [RELEASE.md](RELEASE.md).

**Stage 5a (live watch workout on the phone, implemented in source, not released or device-verified):** a workout started on the watch is followed live and controlled from the phone: the watch mirrors its session (HealthKit workout mirroring, `WCSession.sendMessage` fallback) and broadcasts `session_state`; the phone shows an "Apple Watch workout" page (sets, rest, elapsed time), opens it once per session, and sends idempotent `session_command` messages (log, skip, add a set, rest, pause, resume, finish, discard) that the watch applies once per `command_id` and reports back as applied or rejected. The watch owns the workout, the phone stores nothing for it, no health values travel, and there is no new phone HealthKit permission. A stale or disconnected watch turns controls off. The Swift builds and its tests pass on CI (`watchos_smoke.yml`); the device checks (including whether the `workout-processing` background mode is needed) are open in [RELEASE.md](RELEASE.md).

**Watch reads its own health (sleep, steps, HRV, resting heart rate; implemented in source, not released or device-verified):** the watch Home tiles and detail screens show values read from the watch's own HealthKit store before a phone sync, held in memory only, with the phone winning for sleep, resting heart rate and HRV, steps taking the larger value and scores staying on the phone (ADR-0012 decision 4 amendment). The day rules are a Swift port of the phone's, checked by golden cases in `contracts/watch_link/v1/cases/health/`. Device checks are open in [RELEASE.md](RELEASE.md).

## Phase 5 — User-controlled completed-workout export

Opt-in write of one BeyondRep-owned workout summary, export receipts and platform-specific retry/reconciliation. Avoid double writing Apple Watch `HKWorkout` or Android sessions; imported workouts stay read-only. Resolve app-owned edits/deletion UX before shipping.

## Later phase — Wear OS companion

Wear OS recording (Health Services session, haptics, battery behaviour) is its own later phase, reusing the message format and the shared language-neutral test files from Phase 4, and built when a Wear OS watch is available for device testing. Validate Flutter UI on Wear OS vs Compose before committing; no production dependency on an experimental engine without real tests.

## Diagnostics/privacy cross-cutting gate

Introduce Firebase Crashlytics/Analytics only after privacy disclosure, separate collection controls, explicit native defaults-off configuration and sensitive-payload redaction tests. Add security tests for Supabase RLS, no health cache uploads, data deletion and account boundaries. Run profiling on low-end Android/iPhone/tablet and both watches.

## Deferred product choices

- Adding cloud backup for custom plans/templates (current initial trade-off: they are lost on reinstall).
- Cross-phone recovery of in-progress sessions.
- Platform-workout post-export correction/deletion policy.
- Health cache time-to-live tuning, secure backup exclusions, encryption requirement, server tombstone retention.
- More direct wearable provider APIs and beyond-MVP recovery/readiness calculations (none shipped without validity review).
