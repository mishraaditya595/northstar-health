# NorthStar authenticated completed-workout synchronization

**Policy:** [ADR-0005](adr/0005-mandatory-auth-and-workout-sync.md) (accepted by the owner 2026-10-25) supersedes ADR-0003's optional-login and guest assumptions and keeps its completed-only backup scope. This is a *new product decision*, not an observation about the shipping Flutter app.

**Implementation status (27 October 2026):** P2-01–P2-07 source features are merged: validated completed-only RPC/aggregation, mandatory email OTP and owner-bound offline partitions, atomic outbox, serialized foreground upload/restore, tombstones, reviewed per-workout conflict recovery (#18–#24), Account/sync UI (#25), owner-scoped cloud JSON export (#27), and freshly verified permanent account deletion (#29). **Merged is not hosted deployment, real-account security validation or release.** P2-08 signed-JWT/RLS, two-device, low-memory/native-picker, stale-token/deletion and rollout testing remain outstanding. The worker is **foreground-only**. See [ROADMAP.md](ROADMAP.md), [RELEASE.md](RELEASE.md), and [reviewed conflict recovery](implementation/phase-2/p2-06-reviewed-conflict-resolution.md).

## P2-07c freshly verified permanent account deletion (merged #29; not deployed)

The in-app flow offers cloud-history JSON export before deletion, then sends an OTP to the **currently verified account** with `shouldCreateUser:false`. Verification must establish a *new* Auth session; the server-only `delete-account` Edge Function checks the caller's JWT/user and the read-only `public.authorize_account_deletion()` gate, which requires `auth.sessions.created_at` within five minutes. The function alone uses a server-held service-role credential for Auth hard deletion; foreign-key cascades remove that owner's completed workouts, tombstones, receipts and cursor. Flutter never receives a privileged key. Its binding is cleared and original owner partition locked **before** the remote request. On an exact success response, the app schedules/attempts erasure of **only that original owner's local partition**, retrying confirmed cleanup when safely persisted.

**Uncertain HTTP result ≠ confirmed deletion or confirmed failure.** It keeps the old files locked without automatic erasure and records guarded recovery. Per accepted [ADR-0007](adr/0007-account-deletion-recovery-exit-choices.md), recovery offers **Use another account (keep old data locked)** (clear binding, then recovery marker; retain partition) or **Erase local data and leave** (separate irreversible confirmation, clear binding, erase original owner's partition, then clear marker). Both offer **Keep recovering** cancellation; neither transfers old workouts to a new user. If the original Auth UUID still exists, verified sign-in to it can reopen its own files. Old stateless JWTs may remain cryptographically valid until expiry: independently verify all sync/RLS paths for deleted users. Neither the endpoint nor migration is claimed deployed. See [account deletion runbook](../supabase/ACCOUNT_DELETION_RUNBOOK.md).

## Data classification and account gating

Everyone must register/sign in before using workout features (no guest mode); first authentication requires internet. A securely authenticated account may continue offline, save locally and enqueue changes until the network and auth session can resume. Supabase Auth anonymous accounts are not valid NorthStar accounts.

Cloud accepts *versioned NorthStar-authored phone workouts* only in `completed` state (finished by the user), and deletion tombstones. In-progress, paused and discarded sessions are rejected by the RPC and the table constraint. One aggregate contains session metadata, exercise name/muscle/equipment snapshots, and per-set position/status/type/reps/gram load/unit/RPE/completion time. **This is not a full active-workout checkpoint or plan backup.**

**Never upload:** HealthKit/Health Connect physiological data (HR, HRV, sleep, steps, SpO₂, GPS, etc), imported workouts, raw watch sensor streams, full ObjectBox databases, platform access tokens, app telemetry or device secrets; local recovery timers and editor state; custom plans/templates/catalogs or preferences. Any expansion to exercise notes/durations/RIR requires an explicit versioned DTO change plus privacy/tests.

## Real development schema (P2-01)

- `public.workout_records`: account/workout composite key; one versioned JSONB aggregate; `status`, deletion tombstone, server revision, per-owner `server_change_seq`, and server-derived `completed_working_sets`, `loaded_working_sets`, `loaded_volume_gram_reps`.
- `public.workout_sync_operations`: idempotency receipt keyed by `(user_id,operation_id)`. Holds `request_sha256` (**not the workout payload**), revision and cursor receipt, `committed_at`, `expires_at` (90-day policy).
- `northstar_private.workout_owner_cursors`: per-owner monotonic counter, transactionally advanced. It is not an exposed Data API table.
- `public.sync_workout(operation_id,workout_id,expected_revision,action,payload)`: SECURITY INVOKER wrapper calling an audited private SECURITY DEFINER implementation. Anonymous callers have no EXECUTE grant. Direct client INSERT/UPDATE/DELETE on tables is revoked; owner-only SELECT on records uses RLS. The function derives account identity from `auth.uid()`, not user-supplied JSON.

The first seven migration names/versions are committed P2-01 history; the connected development project currently reports only six, which must be reconciled before deploying P2-05. The merged P2-05 eighth migration adds nullable day-based server progress without changing client upload JSON or request receipts. P2-01 migrations: `20261025060300_phase2_workout_sync_foundation.sql`, `20261025063753_phase2_workout_sync_hardening.sql`, `20261025063912_phase2_validation_coalesce_fix.sql`, `20261025064908_phase2_receipt_expiry_and_security_cleanup.sql`, `20261025070923_phase2_identity_and_tombstone_guards.sql`, `20261025071009_phase2_tombstone_delete_retry_guard.sql`, `20261025090000_phase2_completed_only_scope.sql`. ## Restore feed, foreground importer and reviewed recovery (P2-06)

`public.get_workout_changes(p_after_seq bigint default 0, p_limit int default 100, p_cursor_epoch uuid default null)` returns authenticated owner-only completed-workout snapshots and payload-free tombstones ordered by owner-local `server_change_seq` (max 200 rows per page). The response includes `cursor_epoch`, `next_cursor`, `has_more` and `cursor_reset`. **New clients start at cursor 0 with no epoch; all later calls MUST echo the server epoch.** A private owner state lookup reads the authoritative account counter and database-wide epoch without granting table SELECT access. A missing epoch with nonzero cursor, a mismatched epoch **even after the owner counter overtakes the stale cursor**, or a cursor ahead of the server yields `cursor_reset:true`, `next_cursor:0`, `has_more:false`, `changes:[]` and the new epoch. The client must reconcile queued/acknowledged local updates before replaying from zero, never silently delete them. **Database restore operational dependency:** backup restores the epoch too. Every PITR/snapshot restore must run [the privileged epoch rotation runbook](../supabase/RESTORE_RUNBOOK.md) before serving client reads/writes. No pure SQL flag can reliably infer a restore if the rotation step is omitted. A newly enrolled device can receive tombstones for workouts it never held; this is intentional to prevent resurrection and must not create phantom history entries. The transactional `ObjectBoxWorkoutRestoreImporter` and the serialized foreground restore worker were merged in PRs #20 and #22. PR #24 adds authenticated owner-scoped point lookup, reviewed use-cloud/retry-local/keep-local-only/finish-deletion actions, durable superseding of never-sent blocked uploads, and an explicit retry for blocked restore cursors without skipping a change. Pending or attempted uploads are never silently discarded. A per-workout review can proceed even while the account-wide cursor is blocked; the cursor stays blocked until the user explicitly retries. See [P2-06 implementation](implementation/phase-2/p2-06-restore-and-conflicts.md).

## Disclosure and data rights

The privacy notice and signup flow disclose that finished workouts are backed up automatically. Approved data policy: workout records last until deletion/account closure; tombstones last for the account lifetime; hash-only receipts expire after 90 days. P2-07b (#27) implements a user-triggered authenticated, owner-checked JSON export of completed cloud phone workouts; local-only plans, unfinished workouts, pending uploads and health-platform data are excluded. The in-app permanent account deletion workflow is **implemented in merged PR #29, not hosted-deployed or end-to-end security accepted**; ADR-0007 governs its two uncertain-recovery exits. Export requires independent hosted RLS and native iOS/Android device validation before release.

## Validation and replay

All required object keys must be present with correct JSON types: workout (version, ID, origin, status, name, start, offset, exercises), exercise (ID, name, position, sets), and set (ID, position, kind, status, unit); completed workouts require completion timestamps and performed sets require repetitions + timestamps. Additional fields are **rejected**. IDs must parse as UUIDs, times as ISO-8601 timestamptz, numerical values have bounded ranges and proper JSON number types. Duplicated exercise/set IDs, external origin and health samples are rejected. Maximum aggregate 64 KiB, 120 exercises, 300 sets per exercise.

Validation happens **before** the owner transaction lock and **before** checking remote revisions: a stale *invalid* write is a validation error, not a conflict. Per-user advisory lock plus server-side revision compare-and-swap preserve conflict behavior. A new row uses plain INSERT; an existing row uses conditional UPDATE `WHERE server_revision=expected_revision`. No last-write-wins or overwrite on revision mismatch.

Replay compares SHA-256 of a canonical JSON request tuple (workout ID, expected revision, action, payload) against the stored receipt. A repeated matching operation returns the original acknowledgement; a reused operation ID with different content is a validation error. Response keys are `result` (`applied|conflict`), `revision`, `change_seq`, `replay`, `processing` (`processed|not_applied`). **Never assume the network response means the phone outbox was durably dequeued**; persist the receipt first.

## Processing and missing values

For *completed* workouts only, the server calculates completed working sets, loaded working sets and loaded volume (positive recorded grams times recorded reps). Warmups, non-performed sets, missing/zero loads and unknown states are excluded from loaded volume. A known workout with **no positive recorded weight** stores NULL loaded volume, never a fictional zero. Processing is synchronous in P2-01; no asynchronous worker is implemented yet.

## Retention, deletion, restore and backward compatibility

- A delete writes a tombstone and nulls the primary payload. The receipt stores only a hash. Hash receipts expire after **90 days**. The next authenticated sync opportunistically deletes that owner's expired receipts; `northstar_private.prune_expired_workout_receipts()` also supports a privileged full purge. **Scheduling/monitoring that full purge for inactive accounts remains a release blocker**. When an expired operation is retried, it may return a revision conflict and require reconciliation; never silently overwrite.
- Deleted workout UUIDs are sticky tombstones: a new upsert is rejected with an explicit `reason: deleted` conflict, while a repeated explicit delete is allowed; exact replay remains idempotent. Tombstones are kept until the account is deleted (ADR-0005). Cursor-safe restores still need pagination testing. Do not purge tombstones as if they were receipts.
- There is no guest mode and no guest data to import. Prevent cross-user attachment on logout/switch.
- Account-bound local storage, auth lifecycle and a foreground upload worker are merged in P2-02–P2-04. Mobile foreground restore and durable pull cursors are merged in PRs #20 and #22, with fair upload queue in PR #23. Completed-workout delete commands and explicit reviewed conflict recovery are implemented in PR #24 (not necessarily hosted), and freshly verified permanent account deletion is implemented in P2-07c (#29), subject to hosted and device verification. The feed is consumed by the foreground Flutter importer, not by a background process.
- Only completed workout history can be restored; unfinished sessions never leave the device. Plans, catalog and preferences are not restored.

## Validation, security and rollback

`supabase/tests/workout_sync.test.sql` emits 66 pgTAP assertions with `plan(66)` and standard TAP output, including rejection of in-progress/paused/discarded workouts, RPE 10.5, case-insensitive UUID uniqueness and permanent tombstone protection. It contains synthetic tests for missing fields at each depth, replay and hash-only retention, malformed numeric/timestamp inputs, denial of table writes, owner separation and tombstones. Run `supabase test db` on a **clean** local/CI Supabase stack before merge; the development Supabase SQL execution is additional evidence, not a replacement for clean migration replay or multi-connection concurrency testing.

Always run Supabase security/performance advisors. The fourth migration revoked unauthorized public invocation of the existing `rls_auto_enable()` event-trigger function. Remaining INFO notices for policy-less RLS tables are intentionally deny-all. Privileged/secret API keys, access tokens and database passwords must **never** enter Git or mobile packages; a publishable key can be embedded only with RLS and authenticated server authorization.

**Emergency rollback:** revoke authenticated EXECUTE on the public sync RPC and disable upload retries without deleting server workouts or local outbox. Re-enable only after a tested corrective migration, not by downgrading to the vulnerable original RPC. Do not drop tables containing live user data. Remote migration history is immutable; address schema fixes via additive follow-up migrations.
